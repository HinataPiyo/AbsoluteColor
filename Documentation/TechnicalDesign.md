# 技術設計書

## 1. 開発環境

| 項目 | 確認内容 |
|---|---|
| Unity | `6000.3.13f1`（`ProjectSettings/ProjectVersion.txt`） |
| 言語 | C#。Unity標準の`Assembly-CSharp`／`Assembly-CSharp-Editor`構成。ゲーム用asmdefは確認できない。 |
| 描画 | Universal Render Pipeline。ProjectSettingsにPC／Mobile向けQuality／URP設定がある。 |
| UI | UI ToolkitがゲームUIで使われる。判定表示等にTextMeshProも含む。uGUIパッケージは依存関係にあるが、ゲームでの利用範囲は要確認。 |
| 入力 | Input System 1.19.0を依存に含み、`InputSystem_Actions.inputactions` をプロジェクト設定へ割当。ゲームスクリプトからInput System API／Actionsを使う箇所は確認できず、実操作はUI Toolkitイベント。 |
| 追加パッケージ | Cinemachine 3.1.6、URP 17.3.0、Unity Test Framework 1.6.0、Unityroom client（Git URL）等。 |
| シーン | Build SettingsにHomeScene、GamePlaySceneを登録。 |
| ビルド構成 | Android向けおよびWeb Mobile向けのBuild Profileアセットが存在する。実際のビルド成功・配信ターゲットとしての確定は未確認。 |
| テスト／CI | プロジェクト用テストコード、asmdef、CI設定は確認できない。Test Frameworkパッケージの存在だけではテスト実施を意味しない。 |

依存関係の一次情報は `Packages/manifest.json`。パッケージ一覧は導入状態を示し、全パッケージがゲームコードから利用されていることを意味しない。

## 2. アーキテクチャとクラス設計

- ゲーム進行は `GameManager` がラウンドを逐次進めるコルーチン主体の構成。
- ホーム／ゲーム画面は `UIModuleManagerBase` 派生クラスでUIの初期化をまとめる。
- 個々のUIロジック、採点、結果表示、オーディオ、演出は別クラスへ分かれている。
- 一方、ゲーム進行の中心は具体クラスを複数参照する。依存性注入、インターフェース越しの主要サービス置換、中央イベント集約を行う構造とは確認できない。
- クラス責務の一部は分かれているが、これだけを根拠にSOLID適合や特定デザインパターンの適用を断定しない。

## 3. データ設計

### 編集時データ

- `ColorChannelDataSO`：色チャンネル関連のジャンル／説明／表示名／マテリアルを保持。
- `AudioDataSO`：タグとSE／BGMクリップの対応を保持。
- データをScriptableObjectに置くため、該当するモード情報やクリップ差し替えはロジック変更なしにInspectorから行える。
- ただし、新しいモード固有の挙動や採点方式を追加する仕組みまでデータ駆動化されているとは確認できない。新規種類の動作にはコード変更が必要となる。

### 実行時データ

- モード選択など一部状態は `CoreResource` のstaticプロパティに保持。
- スコア履歴／最高得点はメモリ上のstaticコレクション。
- `ResultData` はラウンド番号・見本色・回答色を持ち、private setterによって生成後の変更を抑止する。
- JSON／ファイル／PlayerPrefs等による永続化は確認できない。

## 4. イベントとゲームロジック

- プレイヤー操作から結果表示までをコルーチンの状態待ちで直列化する。明示的な決定と時間切れが同じ回答提出経路にまとまる。
- UI Toolkitのボタン／スライダーイベントと、結果画面からの進行解除を使用する。
- オーディオ再生はタグでクリップを解決する。判定UI・操作UIが個々のAudioClipを直接参照する形を避けている。
- 色差は正規化RGBの成分別絶対差を平均する単純な指標。色空間変換・知覚色差（例：Lab/ΔE）は確認できない。
- イベント解除の正確性に問題候補があるため、画面再利用／破棄時の登録解除を確認すべきである。

## 5. Unity技術の利用状況

| 技術 | 利用状況・目的 |
|---|---|
| MonoBehaviour | シーン上の管理・表示クラスの基盤。 |
| ScriptableObject | モード／マテリアル、オーディオクリップの編集データ。 |
| Coroutine | ラウンドのタイマー、段階的なゲーム進行、カメラ揺れ等。 |
| UI Toolkit | 画面要素、スライダー、パネル表示、スタイルクラス切替。 |
| TextMeshPro | 判定文字等のテキスト表示。 |
| Cinemachine | カメラ揺れの制御に利用。 |
| Volume / Bloom / Vignette | 判定時の視覚演出。必須参照の未設定を考慮した保護は一貫していない。 |
| Animator／Particle System | 判定アニメーション、最終結果のランク演出。 |
| Input System | パッケージとActionsアセットあり。実際のゲーム操作との結線は未確認。 |
| Addressables、Pooling、DOTS、Burst、Job System | 使用を確認できない。 |
| Editor拡張 | ゲーム固有のEditorツールは確認できない。TutorialInfoのテンプレート用コードはゲーム支援ツールと見なさない。 |

## 6. オブジェクト管理・パフォーマンス

- ラウンド結果を表示する際、`RoundResult` が結果用のUI参照やプレビュー要素を構成し、次ラウンド／結果ボタンを結び付ける。固定5ラウンドのため生成量自体は小さいと考えられるが、繰り返し構築／イベント寿命の整理には改善余地がある。
- UI要素の取得に名前検索を使う箇所があり、取得結果のキャッシュや欠落時診断を整える余地がある。
- オブジェクトプール、Addressables、非同期ロード、GC計測、Profiler結果は確認できない。
- `Instantiate`／`Destroy`やUpdate処理の全体負荷を測定したデータはない。よって最適化済みとは評価できない。
- Mobile向けURP設定（render scale等）は存在するが、対象端末でのフレームレート／画質／メモリ計測は未確認。

## 7. 技術選定の評価

小規模なラウンド制UIゲームに対し、コルーチンで進行を順序付け、ScriptableObjectで編集データを外出しする選択は簡潔で妥当性がある。逆に、静的状態・シングルトン・文字列ベースUI探索・シーン内参照が増えるほど、初期化順序と変更時の破損検出が難しくなる。現段階で過剰なECSやサービス抽象化を追加する根拠は弱く、先に採点整合性、イベント管理、入力検証、テスト可能性を改善する方が費用対効果が高い。

## 8. 技術的課題

1. ランク条件が重なり、一部ランクに到達しない。
2. `MaxScore` と得点式の最大値が一致しない。
3. モード／履歴／オプション等の永続化がなく、セッションをまたぐ状態保持がない。
4. 静的参照・シーン参照に対する初期化／未設定検証が限定的。
5. UIイベントの登録・解除に不具合候補がある。
6. 入力アクションアセットとゲーム操作の責務が明確でない。
7. テストコード、CI、Profiler実測が見当たらず、変更時の自動検証材料が乏しい。

優先度と具体的な改善案は[改善計画](./ImprovementPlan.md)を参照。
