# 技術的課題と改善計画

優先度はユーザーに見える正しさ・クラッシュ／機能不全リスクを基準に付ける。改善案は未実装である。

| # | 優先度／難易度 | 現状・問題点 | 改善案 | 期待される効果 |
|---|---|---|---|---|
| 1 | **P0 / 小** | ランク条件で`>=0.70`が先に評価され、後続の`>=0.80`（Cランク）が到達不能。 | S/A/B/C/Dの期待範囲と境界値を表に定義し、降順に判定する。各閾値の直前・同値・直後をテストする。 | ランク表示の誤りを解消し、変更時の退行を検出できる。 |
| 2 | **P1 / 小〜中** | `MaxScore=750`は得点式の基準値だが、完全一致時の式は整数化前で1312.5点。総合ランクの分母には1.75係数も含まれるため、単純な上限不整合とは限らない一方、定数名が示す意味は曖昧。 | 1ラウンドの最大点、正規化用基準値、総得点、UI表示の意味を明記し、変数名と数式を合わせる。最大／最小／中間値をテスト。 | 得点・割合・ランクの説明が一致し、コード保守時の誤解を減らす。 |
| 3 | **P1 / 小** | `ScoreHistoryComposition`の45行目で`onClick += () => button.clicked += onClick;`としており、ボタンへ履歴項目のコールバックを登録していない。 | ボタンの`clicked`へ意図したハンドラーを直接登録し、実際のUIクリックを含むテストで確認する。 | スコア履歴からの操作が期待どおり動作する。 |
| 4 | **P1 / 小** | `BackButton.Reset()`が登録時とは異なるラムダを解除しようとし、ハンドラーが残る可能性。 | 登録デリゲートを保持し、その同一インスタンスを解除する。画面再初期化を複数回行うテストを追加。 | 重複コールバックや画面遷移後の残存参照を防ぐ。 |
| 5 | **P1 / 小〜中** | モード未設定時のnull、Volume Profile要素の未設定等で例外になる経路がある。 | `Awake`／初期化時に必須参照を検証し、オブジェクト名と不足項目を含むエラーを明示する。任意演出は欠落しても採点／結果表示を継続できるよう分離。 | シーン設定ミスを早期に発見し、Playerでの予期しない停止を減らす。 |
| 6 | **P1 / 中** | `GameManager`が複数の具体クラスとシーン参照に依存し、初期化順序が暗黙的。 | まず依存一覧と初期化順を明文化し、参照検証を追加する。必要になった段階で結果表示／入力待ち等の境界を小さなインターフェースへ分離する。 | 変更時の影響範囲を見つけやすくし、シーン設定の再利用性を高める。過剰な全面改修は避ける。 |
| 7 | **P2 / 小〜中** | `RoundResult`を各ラウンドで生成し、UI参照／リスナーの寿命が明確でない。 | UIをシーン初期化時に一度構成し、各ラウンドでは結果値を渡して更新する。動的生成が必要なら明示的な解除・破棄を行う。 | UI生成・イベント管理を単純化する。5ラウンド環境では性能向上より保守性・安定性が主な効果。 |
| 8 | **P2 / 中** | 履歴・最高点・モード・設定はメモリ上のみで、終了後保持されない。 | 仕様として保存対象を決めた上で、バージョン管理した保存モデルとロード失敗時の復旧を実装する。機密性不要なローカルスコアなら保存方式を要件に合わせて選ぶ。 | 再起動後もユーザー進捗／設定を保持できる。 |
| 9 | **P2 / 小〜中** | `InputSystem_Actions`は汎用Player/UIアクションを定義しProjectSettingsへ割り当てられているが、ゲームスクリプトからInput System API／Actionsを参照する箇所はない。現在の操作はUI Toolkitイベント。 | 現状のUI Toolkit入力だけをサポートするならアセットの用途を明記し、未使用アクションを整理する。Actionsからの操作も要件に含む場合に限り、明示的に接続してUI入力との競合をテストする。 | 入力経路の実態を明確にし、保守時の誤解を防ぐ。 |
| 10 | **P2 / 中** | ゲーム用テスト／CIが確認できず、採点・進行の退行を自動検知できない。 | 色差・得点・ランク・時間式を純粋関数として切り出し、Unity Test Frameworkで境界値テスト。次にUIイベント／コルーチンの統合テストとCIを追加する。 | 採点仕様の改修を安全にし、ビルド品質の再現性を高める。 |
| 11 | **P3 / 中** | UI Toolkit要素の名前を文字列で取得し、誤記や階層変更を実行時まで発見しにくい。 | 共通の安全な取得ヘルパーでnull時に要素名・画面名を診断し、初期化時に必要要素を一括検証する。 | UI変更の不具合を早期に把握できる。 |
| 12 | **P3 / 中〜大** | Mobile向け描画設定はあるが、性能実測・画面サイズ別テストがない。 | 対象端末とフレームレート目標を定義し、ProfilerでCPU／GC／描画／メモリを測定。必要性が確認された処理だけ最適化する。 | 最適化を推測でなく実測に基づいて判断できる。 |

## 推奨実施順

1. ランクと得点の期待仕様を決める（#1、#2）。
2. 履歴ボタン・バックボタンのイベント登録を修正・検証する（#3、#4）。
3. 必須参照の診断と採点単体テストを追加する（#5、#10）。
4. UI生成／static依存／永続化など、実際の製品要件に必要な範囲を選んで改善する（#6〜#9）。
5. 配信ターゲットを確定して実機測定する（#12）。

## 完了条件の例

- すべてのランクが定義された入力範囲から到達可能で、境界値テストが通る。
- 完全一致／最大誤差で期待点と割合が仕様書どおりになる。
- UI初期化を繰り返してもクリックイベントが一度だけ動作する。
- モード／演出参照の不足が無言のnull参照ではなく、設定箇所の分かる診断になる。
- 保存やパフォーマンスについては、対象要件と実測方法を決めたうえで完了とする。
