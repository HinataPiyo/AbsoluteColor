# 実装品質・コードレビュー

## 1. 総評

Unity UI中心の小規模な色合わせゲームとして、ラウンド進行、RGB操作、採点、結果演出を分けて実装している。ScriptableObjectによるデータ外出しや、結果データをまとめて渡す実装は評価できる。一方で、採点・ランク仕様の確認事項、到達不能なランク条件、イベント購読の不具合、参照設定への依存があり、品質を「完成済み」「堅牢」とは評価できない。自動テスト・CI・Profiler計測の証拠も確認できない。

## 2. 項目別評価

| 観点 | 評価 | 根拠・留意点 |
|---|---|---|
| 責務分離 | 一部良好 | RGB入力、採点、表示、音声、演出を別クラスに分ける。一方、`GameManager`が複数システムの具体参照を束ねる。 |
| クラス設計 | 概ね実用的 | `ResultData`の値保持と管理クラスの分離がある。静的共有状態／シングルトン依存が強く、単体差し替えや独立テストは容易でない。 |
| 命名 | 混在 | 意味を表す名前が多いが、`JugementUI`、`AdjustRGBSlidedr`等の綴りに一貫性の問題がある。 |
| 可読性 | 中程度 | `GameLoop`の順序は追いやすい。UI要素の文字列パス、static状態、シーン参照の全体像を同時に追う必要がある。 |
| 再利用性 | 限定的 | 共通UI基底クラス、SOデータ、RGB調整の類似実装がある。ホーム／ゲーム間でRGBロジックは完全な共通化とは確認できない。 |
| 拡張性 | 小規模機能には対応 | SOの既存項目の変更・追加に対応しやすい。新しい採点方式やモード挙動追加はコードとUIの変更を伴う。 |
| 保守性 | 改善余地 | 文字列参照、静的状態、イベント解除、Inspector設定の検証が不足。 |
| 依存関係 | 要注意 | `GameManager.I`等のシングルトン／static参照とシーン内依存。初期化順序・テスト分離・欠落参照に影響。 |
| エラー処理 | 不十分な箇所あり | nullになり得るデータ取得、Volume Profile要素等の検証に不均一さがある。 |
| メモリ管理 | 小規模範囲 | 5ラウンドとUI規模から大きな負荷の証拠はない。一方、結果クラスの繰り返し生成とイベント寿命は整理可能。Profiler未確認。 |
| パフォーマンス | 実測なし | Mobile向けURP設定はあるが、フレーム時間・GC・メモリ計測は見当たらない。最適化済みとは判断できない。 |
| テスト容易性 | 低〜中 | 色差と得点は純粋計算に近くテスト可能だが、Unityシーン／static依存がある。プロジェクトテストは見当たらない。 |
| Unity特有の設計 | 実用的だが依存リスク | コルーチン、SO、UI Toolkit、Cinemachine、Volumeを使う。Inspector割当・実行順・シーン破棄の検証を強化したい。 |

## 3. 確認された問題点

### 3.1 採点とランクの仕様確認事項

- `MaxScore=750`は得点式の基準値だが、完全一致時は係数1.75を掛け、整数化前で`750×1.75=1312.5`となる。総合ランク計算でも分母に1.75を含むため、数式の内部矛盾とは断定できないが、`MaxScore`という名前とUI表示の意味を明確にすべきである。
- `scorePercentage >= 0.70`の条件が後続の`>= 0.80`より先に判定されるため、Cランク条件に到達しない。ランク順はS `>=0.95`、A `>=0.90`、B `>=0.70`、C `>=0.80`、それ以外D。
- 総得点の正規化値、ランクの区分、UI表示を含めて、期待するスコア仕様を明文化する必要がある。

根拠：`Assets/Scripts/Constants/ValueConstants.cs:5-44`

### 3.2 UIイベントの登録・解除

- `ScoreHistoryComposition`の45行目は `onClick += () => button.clicked += onClick;` となっており、ローカルなデリゲートを変更するだけでボタンの`clicked`へ履歴項目処理を登録していない。クリック時に期待処理が実行されない。
- `BackButton.Reset()`は登録時と異なる新しいラムダで解除を試みるため、元のハンドラーを解除できない。

根拠：`Assets/Scripts/Home/ScoreHistory/ScoreHistoryComposition.cs:32-45`、`Assets/Scripts/Constants/BackButton.cs:13-37`

### 3.3 null／Inspector設定への依存

- `CoreResource.GetColorChannelData()`はPlayer実行時にデータ未設定ならnullとなる可能性がある。
- 判定演出の初期化時にVolume／Profile要素が不足しても、後続処理でBloom／Vignetteを参照する経路がある。
- Singleton／シーン参照の初期化順序やInspector未割当を統一的に検証する仕組みが限定的。

根拠：`CoreResource.cs:10-33`、`JugementUI.cs:57-67,100-104`、各シーン上の管理クラス参照。

### 3.4 状態保持と実行時生成

- 履歴・最高点・選択モード・オプションに、アプリ再起動をまたぐ保存は確認できない。
- ラウンド結果表示では `RoundResult` が結果用UI参照やプレビュー要素を構成し、ボタンコールバックも保持する。全5ラウンドのため現状で大量生成ではないが、UI参照／イベントの寿命を明確にする余地がある。

根拠：`CoreResource.cs:35-66`、`Option.cs:15-43`、`ResultController.cs:103-117`、`RoundResult.cs:14-53`

## 4. 良い点

1. **ゲームの主ループが追いやすい**：開始、入力、時間、結果、次ラウンドがコルーチンで連続する。
2. **色入力が体験と直結する**：RGB各値がプレビューと結果計算へつながる。
3. **編集データの外出し**：色素材・説明や音声クリップをScriptableObjectで保持する。
4. **結果データのまとまり**：見本色・回答色・ラウンド情報を値オブジェクトとして渡す。
5. **結果演出の分離**：採点値とカメラ／音声／ポストプロセス／パーティクルの責務が一定程度分かれている。

## 5. 未確認事項

- Unity Editor上でのシーン参照／UIDocument／Volume Profile設定の完全性。
- Web／Android等のビルド成功、端末別入力・画面比率・パフォーマンス。
- Unityroomランキングの接続先・認証・送信成功率。
- 色の見え方、閾値、時間制限に関するユーザーテスト。
- テストコード、CI実行、Profiler計測の存在はリポジトリ内で確認できない。

## 6. まとめ

本作は、ゲームループとUI連携の全体像を説明しやすい一方、採点の正当性とイベントの確実性が未完成である。ポートフォリオでは「設計済み」と過大表現せず、問題を発見した根拠と、仕様決定からテスト追加までの改善方針を説明するのが適切である。
